# Existing Android bridge review

Reviewed 2026-10-11. **Neither candidate is suitable as the execution boundary for this prototype without substantial removal of capabilities and a separate local authorization design.** Both are application-level bridges. Neither replaces Android, constitutes a Pixel 9a ROM, or establishes Pixel 9a compatibility by itself. No candidate code or binary has been incorporated into this repository.

This is a targeted source review, not a full security audit. It covers the manifests, MCP admission/dispatch, selected Android execution paths, credentials, tunnel transport, and available test evidence. Upstream setup scripts and APKs were not executed. Git clone failed because this environment's configured proxy was unreachable; primary files and repository metadata were then read through the GitHub connector. All code links below pin the reviewed revision. The review does not verify the user's access to the upstreams' described OpenAI tunnel product or current ChatGPT client behavior.

## Android-ChatGPT-Remote

- **Execution:** [`McpTransport.kt`](https://github.com/charifmahmoudi/Android-ChatGPT-Remote/blob/18f89754f5052c51c1796bb72d640e569d1cc2b6/app/src/main/java/com/charifmahmoudi/chatgptremote/McpTransport.kt#L77) dispatches `adb_status`, `adb_shell`, `adb_packages`, and `adb_properties`. `adb_shell` accepts a caller-supplied string, checks its length (1–8,192 characters), and passes it to `adb.shell(command)`. There is no command allowlist or on-device per-command approval in this path. An authenticated remote agent receives the privileges of the paired Android shell user. Root is not required, but shell authority is substantially broader than opening a small fixed set of approved applications.
- **Transport and authentication:** [`TunnelClient.kt`](https://github.com/charifmahmoudi/Android-ChatGPT-Remote/blob/18f89754f5052c51c1796bb72d640e569d1cc2b6/app/src/main/java/com/charifmahmoudi/chatgptremote/TunnelClient.kt) implements outbound long polling and correlated responses, using an `Authorization: Bearer` runtime key. The production service uses `https://api.openai.com`; local ADB is paired over loopback. There is no inbound public MCP listener. Android platform TLS trust is used. This authenticates the connection; it does not constrain the command's purpose.
- **Credentials and permissions:** [`SecureConfig.kt`](https://github.com/charifmahmoudi/Android-ChatGPT-Remote/blob/18f89754f5052c51c1796bb72d640e569d1cc2b6/app/src/main/java/com/charifmahmoudi/chatgptremote/SecureConfig.kt) uses Keystore-backed encrypted preferences. The [manifest](https://github.com/charifmahmoudi/Android-ChatGPT-Remote/blob/18f89754f5052c51c1796bb72d640e569d1cc2b6/app/src/main/AndroidManifest.xml) requests Internet, foreground-service/special-use, and notification permissions, disables backup and cleartext application traffic, and does not export the tunnel service. It declares no accessibility service or direct SMS/call permission. Wireless debugging pairing is a separate, powerful grant.
- **Reliability:** The tunnel has a bounded queue, four workers, retry/backoff, and deadline handling. The ADB connection is recreated per call and readiness depends on a shell probe plus tunnel connectivity. These are useful safeguards, but they do not prove survival across Pixel wireless-debugging port changes, reboot, Doze, process termination, or network transitions. Cancellation of a transport exchange is not proof that a remote side effect did not happen.
- **Test evidence:** The pinned commit's [CI run](https://github.com/charifmahmoudi/Android-ChatGPT-Remote/actions/runs/35044234770) reported successful `build-test` and `emulator-test` jobs. The [workflow](https://github.com/charifmahmoudi/Android-ChatGPT-Remote/blob/18f89754f5052c51c1796bb72d640e569d1cc2b6/.github/workflows/android.yml) includes unit tests, lint, APK assembly, and API 35 x86_64 emulator instrumentation with a provisioned ADB identity. This is upstream CI evidence, not a local rerun or a Pixel 9a hardware test. The releases API returned no releases; the README distributes a debug APK through CI.
- **Reuse assessment:** Keep the design lessons about bounded work and honest health reporting. A useful narrow fork would remove `adb_shell`, package/property dumps, and preferably ADB entirely; introduce typed application/alarm operations with local review and a device-side allowlist; and then re-test the complete transport and execution path. That change is large enough that the small native prototype is easier to reason about.

## DroidBridge

- **Execution:** The [README](https://github.com/zephyr7030/DroidBridge/blob/f00574f5425d348dcce6b447ac449a91e071079b/README.md) describes `context`, `visual`, `android`, `filesystem`, `command`, `network`, `automation`, and `task_control`. Actual [`command.rs`](https://github.com/zephyr7030/DroidBridge/blob/f00574f5425d348dcce6b447ac449a91e071079b/rust/crates/runtime/src/command.rs#L301) validates size, timeout, and identity, then executes the supplied command using a shell `-c` argument. This is intentionally general shell execution, as app, Shizuku shell, or root depending on granted capabilities; bounds and identity validation are not a command-purpose allowlist.
- **Application and intent surface:** [`android.rs`](https://github.com/zephyr7030/DroidBridge/blob/f00574f5425d348dcce6b447ac449a91e071079b/rust/crates/runtime/src/android.rs#L488) validates package/component/URI structure and sizes. [`AndroidMotherToolPlatformAccess.kt`](https://github.com/zephyr7030/DroidBridge/blob/f00574f5425d348dcce6b447ac449a91e071079b/standalone/src/main/java/com/droidbridge/standalone/execution/android/AndroidMotherToolPlatformAccess.kt#L57) launches supplied packages and builds activities from supplied actions, data, components, and extras. The reviewed paths do not constrain execution to this prototype's fixed application list and one alarm operation. Notification actions and clipboard access further widen the surface.
- **Accessibility:** The [service configuration](https://github.com/zephyr7030/DroidBridge/blob/f00574f5425d348dcce6b447ac449a91e071079b/standalone/src/main/res/xml/accessibility_service.xml) requests window content, interactive windows, screenshots, and gestures. The [implementation](https://github.com/zephyr7030/DroidBridge/blob/f00574f5425d348dcce6b447ac449a91e071079b/standalone/src/main/java/com/droidbridge/standalone/execution/android/DroidBridgeAccessibilityService.kt) contains screenshot, hierarchy, and UI-input functionality. This is broad cross-application access once enabled, not a substitute for semantic approval of each user task.
- **Local MCP:** [`mcp_listener.rs`](https://github.com/zephyr7030/DroidBridge/blob/f00574f5425d348dcce6b447ac449a91e071079b/rust/crates/runtime/src/mcp_listener.rs#L38) binds IPv4 loopback; documented app/root endpoints are `http://127.0.0.1:8765/mcp` and port 8766. [`mcp.rs`](https://github.com/zephyr7030/DroidBridge/blob/f00574f5425d348dcce6b447ac449a91e071079b/rust/crates/runtime/src/mcp.rs#L427) checks method, Host, Origin, and bearer token. Token comparison folds byte differences after length checking. [`McpSettingsController.kt`](https://github.com/zephyr7030/DroidBridge/blob/f00574f5425d348dcce6b447ac449a91e071079b/standalone/src/main/java/com/droidbridge/standalone/runtimehost/McpSettingsController.kt) creates 32 random token bytes, saves the local token in an owner-only configuration file, and supports rotation. Loopback alone would not isolate it from other local apps; the token is an important boundary.
- **Remote tunnel:** [`tunnel.rs`](https://github.com/zephyr7030/DroidBridge/blob/f00574f5425d348dcce6b447ac449a91e071079b/rust/crates/runtime/src/tunnel.rs#L28) uses `https://api.openai.com/`, bearer credentials, Rustls TLS configuration, and disables redirects. The standalone app's [`TunnelSettingsController.kt`](https://github.com/zephyr7030/DroidBridge/blob/f00574f5425d348dcce6b447ac449a91e071079b/standalone/src/main/java/com/droidbridge/standalone/runtimehost/TunnelSettingsController.kt#L61) encrypts the runtime key using Keystore AES-GCM and the tunnel ID as authenticated associated data. The source's description of a pinned root store should not be read as pinning one server certificate. No live tunnel was connected in this review.
- **Permissions:** The [standalone manifest](https://github.com/zephyr7030/DroidBridge/blob/f00574f5425d348dcce6b447ac449a91e071079b/standalone/src/main/AndroidManifest.xml) includes Internet/network access, foreground service/media projection, boot reception, notifications, exact alarms, installation requests, and battery-optimization exemption requests. It declares notification-listener and accessibility services; the latter is protected by `BIND_ACCESSIBILITY_SERVICE`. Shizuku/root and user-granted special access are additional authority. The manifest does not request direct `SEND_SMS`, `READ_SMS`, or `CALL_PHONE` permission. That absence does not make arbitrary UI or privileged shell automation harmless to messaging or phone apps.
- **Authorization limitation:** The tool catalog publishes MCP safety annotations, including destructive/read-only hints. Hints are information for the client, not a device-side confirmation barrier. The README explicitly says there is no extra remote permission layer; the agent obtains the access granted on-device. The reviewed broad execution paths offer no evidence of the narrow per-action approval policy required here.
- **Reliability and test evidence:** The source tree contains Rust tests for contracts, admission, persistence, runtime, MCP, commands, networking, automation and recovery, plus Kotlin unit and Android device tests. The inspected listener bounds connections and header/body read time; the latest host-slot change adds a ten-second busy response. These are promising engineering controls. GitHub's Actions-runs collection returned no runs, so this review cannot claim verified upstream CI passes. Release records list an ARM64 app, signature/manifest/checksum artifacts and root module; their presence is not verification that a downloaded binary matches this commit. No tests or APKs were run here, and no Pixel 9a device was available.
- **Reuse assessment:** Its richer runtime is worth studying if a later product needs guarded jobs or MCP transports. Adopting it now would require removing shell, filesystem, network, arbitrary intents, notification actions and visual control from both tool discovery and every direct execution route; adding local per-action review; and demonstrating that disabled routes cannot be reached through alternate APIs. Merely hiding tools in the planner prompt would leave authority intact.

## What this means for the prototype

The initial executor should use ordinary Android APIs: launch only named, preselected applications, and hand an alarm request to the clock UI for the user to review. It does not need Wireless debugging, Shizuku, root, an accessibility service, SMS/call access, an Internet listener, or cloud-held device-control credentials.

No SMS or phone-call operation is implemented or validated by this review. Neither manifest's lack of direct SMS/call permission proves that its general tools cannot affect those apps. Such operations need their own explicit task model, permissions, local review, and device tests before integration.

If upstream code is later reused, pin the reviewed commit, retain the appropriate Apache license and notices, record modified files and dependency licenses, review the changed execution paths, and test the built artifact on the intended Pixel build. The current source observations are not a claim of production readiness or a reason to install a broad bridge for this narrow experiment.
